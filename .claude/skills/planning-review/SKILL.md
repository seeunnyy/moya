# Planning Review

기획서를 코드로 옮기기 전에, 구현을 막거나 나중에 뒤집힐 구멍을 찾는다.
리뷰만 하고 기획서는 고치지 않는다. 사용자가 반영을 요청하면 그때 수정한다.

## 입력

1. 기획서 Markdown 파일 경로, 대화에 붙여넣은 본문, 또는 노션 페이지.
2. 노션 링크만 받았다면 연결된 Notion 도구로 읽는다. 읽지 못하면 내용을 추측하지 말고, 못 읽었다고 말한 뒤 Markdown으로 내보내 달라고 요청한다.
3. 입력이 없으면 기획서 위치부터 묻는다.
4. 프로젝트 지침이나 CLAUDE.md에 일정·기술 스택·팀 구성이 있으면 함께 반영한다.

## 리뷰 순서

기획서를 끝까지 읽은 뒤 아래 순서로 점검한다. 문제가 없는 항목은 건너뛴다.

### 1. 한 문장 연결
문제 → 타겟 → 해결 방식 → 차별점이 한 문장으로 이어지는지 확인한다. 이어지지 않으면 어디서 끊기는지 짚는다.

### 2. MVP 범위
- 기획서의 모든 기능을 MVP / 베타 / 제외로 분류한 표를 만든다.
- MVP에 핵심 플로우와 무관한 기능이 섞여 있으면 베타로 내리기를 제안한다.
- 외부 API·유료 서비스 의존을 모두 나열하고, 없앨 수 있는 것과 대체안을 적는다.

### 3. 핵심 사용자 플로우
- 첫 진입부터 핵심 가치를 경험하는 순간까지 화면 단위로 따라간다.
- 끊기는 지점, 정의되지 않은 화면, 첫 실행·빈 상태·권한 거부 상태가 있는지 본다.

### 4. 모호한 표현
"똑똑하게", "적절히", "자연스럽게"처럼 검증할 수 없는 표현을 찾아, 확인 가능한 기준으로 바꾼 문장을 제안한다. 기획서에 없는 수치를 사실처럼 만들지 않고, 제안값은 "(제안)"으로 표시한다.

### 5. 모순과 충돌
기능끼리, 또는 기능과 컨셉·세계관이 서로 어긋나는 곳을 찾는다.

### 6. 예외·실패 상황
기능마다 실패했을 때 사용자가 무엇을 보는지 정의돼 있는지 확인한다. 최소한 입력 실패, 네트워크 오류, 결과 없음, 권한 거부를 본다.

### 7. 사용자 안전·데이터
대상 사용자가 아동이면 부적절한 콘텐츠 처리, 음성·개인정보 수집과 저장, 보호자 동의를 반드시 확인한다.

### 8. 구현 가능성
- 일정 안에 만들 수 있는지, 가장 불확실한 기술 요소가 무엇인지 짚는다.
- 리스크가 큰 요소는 시연용 대체안(목업 응답, 하드코딩 예시 등)을 함께 제안한다.

### 9. 시연 관점
- 발표 시간 안에 보여줄 데모 시나리오가 성립하는지 확인한다.
- 차별점이 설명이 아니라 화면에서 눈에 보이는지 확인한다.

### 10. 스펙 변환 준비도
md-to-openspec으로 바로 요구사항과 시나리오를 뽑을 수 있을 만큼 구체적인지 판정한다.

## 출력 형식

```markdown
# 기획서 리뷰: <문서 제목>

## 판정
진행 가능 | 보완 후 진행 | 재검토 필요 — 이유 1~2문장

## [필수] 구현 전에 정할 것
1. **<문제 요약>** — 근거: <섹션명 또는 짧은 원문>
   - 문제: …
   - 수정안: …

## [권장] 정하면 좋은 것
(같은 형식)

## MVP 범위 표
| 기능 | 기획서 표기 | 제안 | 이유 |
|---|---|---|---|

## 외부 의존
| 항목 | 용도 | 없앨 수 있나 | 대체안 |
|---|---|---|---|

## 데모 시나리오 (제안)
1. …

## 열린 질문 (사용자가 결정)
- [ ] <질문> — A / B (권장: A, 이유)

## 유지할 결정
- …

## 범위 확장 아이디어 (선택)
- …

## 다음 단계
- [필수] 항목 해결 → md-to-openspec 실행
```

## 작성 규칙

- 지적마다 기획서의 섹션명이나 짧은 원문을 근거로 붙인다.
- 지적에는 항상 수정안을 함께 쓴다.
- [필수]는 구현을 막거나 시연을 망칠 문제만 넣고 5개 이내로 추린다. 나머지는 [권장]으로 내린다.
- 전체 지적은 12개를 넘기지 않는다. 사소한 표기 문제는 한 줄로 묶는다.
- 새 기능 아이디어는 [필수]/[권장]에 넣지 않고 "범위 확장 아이디어"로 따로 둔다. 기본 방향은 MVP 축소다.
- 사용자가 결정할 일은 대신 정하지 말고 선택지와 권장안을 함께 제시한다.
- 기획서에 없는 내용을 있는 것처럼 쓰지 않는다. 추정은 "(추정)"으로 표시한다.
- "유지할 결정"은 뒤집지 말아야 할 것만 짧게 쓴다.

## 저장

파일을 쓸 수 있는 환경이면 리포트를 `planning/reviews/<기획서파일명>-review.md`에 저장하고 경로를 알려준다. md-to-openspec이 이 파일을 함께 읽는다.
파일을 쓸 수 없는 환경이면 대화에 출력만 한다.

## 모야 프로젝트 참고 맥락

기획서에 다르게 적혀 있으면 기획서를 따른다.

- 서비스: 아이가 모르는 단어를 "○○이 뭐야?"라고 음성으로 물으면, 외계인 친구가 쓰인 맥락과 함께 설명해주는 어휘 학습 모바일 웹 (2026 4호선톤 출품)
- 차별점: 아이 발음이 부정확해도 상황 맥락으로 의도한 단어를 유추해 제시
- 이미 정한 범위: 외부 API 최소화, 반복 학습·부모 리포트는 베타
- 꼭 점검할 쟁점: "외계인에게 지구 말을 알려준다"는 세계관과 "아이가 단어를 배운다"는 학습 구조가 화면 흐름과 외계인 대사에서 충돌하지 않는지
